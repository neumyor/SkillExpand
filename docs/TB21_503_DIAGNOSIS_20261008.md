# TB2.1 reviewer 503 diagnosis (2026-10-08)

## Confirmed failure chain

The Tencent DeepSeek endpoint returned HTTP 400 with upstream error code
`400006`: `This model does not support the requested response_format or output
format.` The outer error also contains code `102503`, which is not the HTTP
status. The actual E5 task 11 reviewer prompt reproduced this failure in 2.57s.

The previous relay hid the cause in two steps:

- It searched arbitrary command stderr for `429` and `timeout`. A request ID
  containing `4296` was misclassified as rate limiting; a traceback source line
  containing `urlopen(req, timeout=...)` was misclassified as a timeout.
- It mapped the remaining provider errors to HTTP 503. The legacy client then
  described this as an overloaded or unavailable server.

This establishes a source of the observed 503s, but does not prove that every
historical 503 had this cause: those runs did not preserve the original error.

## Evidence

All probes used Tencent E2B and `deepseek-v4-flash-0731-tencent`, thinking enabled,
without an explicit output-token limit. Diagnostic outputs are separate from
experimental results under `/data2/liyishan/SkillExpand-tb21/SkillExpand/runs/`:

- `tb21-20261008-relay503-diagnostic`: plain prompt, 6/6 succeeded.
- `tb21-20261008-relay503-schema-diagnostic`: strict reviewer schema, 4/6
  succeeded and 2/6 returned the unsupported-format HTTP 400. This demonstrates
  inconsistent acceptance of the parameter; the provider's routing internals
  have not been inspected.
- `tb21-20261008-reviewer-format-diagnostic2`: actual E5 task 11 prompt with
  strict schema, HTTP 400 / 400006 reproduced. Original error is now retained.
- `tb21-20261008-reviewer-noformat-diagnostic`: same actual prompt without
  `response_format`; succeeded in 129.11s with valid reviewer JSON containing
  `probability_true=0.62`, `predicted_success=true`, and a nonempty reason.
  This is a diagnostic response, not an accepted experimental score.

An initial actual-prompt probe failed to create its sandbox because the old
forced startup command was used. The repeat used the healthy template default.
That control-plane failure is separate from the provider-format failure.

## Repair and experiment boundaries

The relay now emits and parses an explicit JSON error record containing the
provider HTTP status, instead of classifying arbitrary traceback text. It
preserves 400, 429, and 5xx responses and redacts the API key in diagnostics.
Focused tests: 14 passed, including status preservation and misleading request
IDs / timeout text.

No diagnostic response is imported into reviewer caches, gate scores or
commits. No formal reviewer protocol, correction budget or historical result
has been changed. Omitting wire `response_format` is a potential compatibility
repair, but must retain prompt/schema validation and be recorded in a new run's
protocol and cache identity. Resuming requires reconciling the relay code change
with the run's code-signature audit; do not bypass that check.
